# 资料库检索

## 目标

让全部资料参与候选判断，但只把高相关内容放进上下文。检索结果用于内部综合，不作为最终产品方案的引用附录。

## 定位资料库

1. 优先使用用户明确指定的资料库目录。
2. 未指定时，从当前工作区向上查找同时包含 `AGENTS.md` 和多个 `*-收录.md` 的目录。
3. 无法可靠确定时，只询问一次资料库位置。
4. 不把绝对目录写入最终文档，也不在 Skill 内硬编码某台机器路径。

## 建立索引

Python 可用时运行：

```bash
python scripts/kunpeng.py index --library <资料库目录>
```

默认索引位于资料库的 `.kunpeng-cache/library-index.json`。索引收集 `*-收录.md` 及标准命名的品牌、视觉、UI、方法和技术蒸馏文档，只保存相对路径、章节文本、文件状态和必要统计；文件未变化时复用旧条目。

Python 不可用时，用宿主搜索能力读取文件名和以下章节：项目介绍、适合参考的方向、核心功能、技术栈、UI/交互亮点、值得借鉴、缺点。

## 构造查询

从产品简报提取 3–4 组短查询，分别覆盖：

- 用户、问题和行业。
- 产品形态与主要能力。
- 品牌、视觉和内容气质。
- UI、交互和特殊场景。
- 技术限制、团队和部署。
- 风险、缺点和反例。

不要只用产品名称搜索。用同义词和结果描述补充查询，但不要生成几十个低价值关键词。

## 检索与深读

```bash
python scripts/kunpeng.py search --index <索引文件> --query "查询内容" --limit 6 --max-chars 8000
```

1. 先合并多组查询结果，并按主体身份去除同一项目的重复收录。
2. 按问题匹配、产品形态、用户场景、约束和可迁移性重新排序。
3. 默认深读 3–6 个条目，任何规划任务都不得超过 8 个。
4. 先用检索片段和命中章节完成判断；最多展开 2 份全文。
5. 至少检查一个缺点或反例明显的条目，防止只吸收成功叙事。
6. 达到预算后必须进入综合，不继续搜索相似案例。

检索分数只代表文字相关，不代表方案适合。最终取舍必须结合预算、团队、平台、维护和用户任务。

## 内部综合

为每项候选建议内部记录：

```text
适配问题 | 适用条件 | 可迁移规律 | 代价 | 冲突 | 确信度
```

对重复规律合并，对矛盾规律按条件拆分。原项目技术栈只能证明一种实现方式，不能自动成为新产品推荐。

## 对外隐藏

产品方案、视觉方案和技术方案中不得出现：

- `*-收录.md` 文件名或资料库路径。
- “参考了某项目”“借鉴自某方法”等归因。
- 检索关键词、排名、分数和候选清单。
- 内部事实卡、来源映射或证据索引。

可以正常写推荐的技术、设计规则和方法，但直接解释它为什么适合当前产品。

## 更新策略

- 新增或修改收录文档后增量重建索引。
- 索引损坏或版本不匹配时完整重建，不修改原收录文件。
- 技术时效性高的结论在使用前核对当前官方资料。
- 首轮方案不做开放式网络调研；确需核对兼容性、价格或平台政策时，最多检查 3 个官方页面。
- 索引只提高检索速度，不替代对关键原文的核查。
