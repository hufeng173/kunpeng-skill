# 项目收录规范

## 定位

生成供以后交给人或 AI 再分析的内部项目档案。不要写成 README、教程、宣传稿或逐文件源码说明。

文件名使用 `项目名-收录.md`。中文项目名通常控制在 2–8 个字；公开源码或体验地址放在项目介绍开头。单文件不得超过 250 行。

本地仓库先运行安全盘点，再由宿主沿真实入口和调用链阅读：

```bash
python scripts/kunpeng.py repository <仓库目录> --output <证据目录>
```

在线仓库或产品页面按 `source-routing.md` 采集并登记宿主证据。收录档案可以停在忠实事实整理；若用户还要求抽取可迁移方法或用于新项目，必须继续完成事实卡、画像和质量门，不能把收录文档当成蒸馏画像。

## 输出结构

```markdown
# 项目收录

## 1. 项目介绍
## 2. 适合参考的方向
## 3. 核心功能
## 4. 技术栈
## 5. 项目结构
## 6. 核心流程
## 7. 数据流
## 8. 外部依赖
## 9. UI/交互亮点
## 10. 值得借鉴
## 11. 整理重点
## 12. 缺点
## 13. 运行方式
```

## 1. 项目介绍

用 2–4 段说明：项目是什么、解决什么问题、核心能力和主线是什么。二次开发、客户定制、内部控制台和生态附属模块只简要定位，不盖过本体。

## 2. 适合参考的方向

按真实能力选择网页、App、Agent、3D、后台、工作流、可视化、企业工具、自动化、桌面端、游戏或插件生态等方向。每条写清具体参考价值，不硬凑分类。

## 3. 核心功能

只列主线功能。每条说明用户能感知什么，以及系统大致依靠什么支撑。排除未接入依赖、演示残留和僵尸功能。

## 4. 技术栈

按实际情况描述前端、后端、数据库、Agent、3D、部署和其他能力。库名后必须说明承担的作用；未观察到就省略或写“未体现”，不得猜测。

## 5. 项目结构

- 使用项目根目录相对路径，不出现磁盘根路径或个人目录。
- 按模块合并，控制在 25 条以内。
- 每条只说明该目录或关键文件承担什么职责。
- 在线成品无源码时改写为页面、路由和公开资源结构，并明确这是体验结构。

## 6. 核心流程

分为“用户怎么用”和“系统内部怎么处理”。前者写主要任务路径，后者写前端、后端、服务、数据库、外部 API、任务、Agent、3D 等如何协作。

## 7. 数据流

按“输入、处理、存储、输出”组织。区分用户输入、配置、外部数据、模型输入、文件和数据库数据，写真实链路而非概念描述。

## 8. 外部依赖

按实际情况写模型、API、数据库、推送、认证、文件/对象存储和第三方服务。只写类型、作用和可确认边界，不写真实凭据。

## 9. UI/交互亮点

必须说明整体布局、导航、主工作区、表单、列表、卡片、日志、弹窗和状态提示怎样配合。存在 3D、Canvas、地图、编辑器或游戏场景时，说明其位置、输入方式、状态变化和业务作用。用可观察特征解释美观度。

## 10. 值得借鉴

写可迁移的设计思想及其价值，不重复核心功能。说明为什么有效、适合什么条件；不要只写“值得参考”。

## 11. 整理重点

告诉后续读者优先看什么、主线从哪里开始、哪些是附属功能、哪些目录容易误判，以及二次分析应沿什么路径展开。

## 12. 缺点

从用户体验、产品呈现、功能逻辑、信息架构、使用门槛和交互一致性写 5–8 条。不要把该节写成源码 Code Review。

## 13. 运行方式

只写必要的安装、启动、测试和构建命令。命令不确定时明确以项目 README 或脚本为准，不写教程式提醒。

## 媒体处理

截图或视频只在能证明布局、状态或交互时加入。优先放到独立素材目录或短小附录，不设置空章节，也不让媒体清单挤占主档案。

## 收录自检

- 核心功能、技术栈、核心流程、数据流、外部依赖、UI/交互亮点和整理重点是否完整？
- 是否完整阅读主线，而非只看 README 或首页？
- 是否泄露身份、凭据、私有配置或个人绝对路径？
- 是否把附属模块、概念路线或依赖误写成已实现核心？
- 项目结构是否根目录相对、分组清楚且不超过 25 条？
- UI 是否写了布局、状态和交互？
- 缺点是否主要来自产品与体验？
- 全文是否紧凑、无宣传腔、无重复且不超过 250 行？
